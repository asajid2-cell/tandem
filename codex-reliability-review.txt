THE FIX I JUST SHIPPED (server/fireEngine.js `maintainBlare` + scheduleBlareMaintain + server/lmsClient.js): while an alarm is BLARING a watchdog re-asserts every blareMaintainMs (~2500ms). KEY INSIGHT = re-assert with WRITES (reliable), never depend on READS (LMS `mode ?` reads were timing out under load → missed re-asserts → the box's pause stuck). Each tick now UNCONDITIONALLY: `power(true)` + `lms.resume()` (= `<player> pause 0`, which resumes a PAUSED box WITHOUT restarting a PLAYING one — bare `play` RESTARTS the track from 0, I verified this on the Boom) + `setVolume(>= floor)`. Reads (mode/volume) are best-effort with a SHORT 1200ms timeout (lmsClient `command(cmd,{timeoutMs})`), used only to honour a knob-down + detect a genuine `stop` (→ playLooping re-load) — they NEVER block the re-assert. Floor = `max(blareMinAudible=6, target × (1 − maxDampening/100))` — NEVER 0; target also floored at 6. `maxDampening` is a global setting (settingsStore, default 70%) injected at fire time via the scheduler onFire. The watchdog ALWAYS re-arms (even after a thrown tick) and only a dismiss (token bump + phase change) ends it. `doStopRing` has ownership detection (only touches the box if the alarm's own track is what's playing). 67 vitest pass; a live 50%-volume soak passed (12 box presses over 5 min → stayed ringing, dampened 50%→15% floor, never silent, never stopped; website dismiss → clean stop, no phantom).
